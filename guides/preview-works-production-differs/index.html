Why Preview Works but Production Differs

The app looked fine on localhost or a preview URL. Production—or “real users”—behaves differently: auth redirects, empty data, missing keys, wrong API hosts. You need a parity worksheet, not a panic rebuild.

Author: AppRescue. Reviewed 13 September 2026. Technical claims about environment scopes, redeploy behavior, and NEXT_PUBLIC_ inlining are tied to the vendor docs listed below.

Preview success is not production proof. Keep sensitive logs and screenshots in a private place you control. The Release Evidence Check is browser-local and self-report only. It does not accept uploads. Record non-sensitive evidence labels and status there. Never paste secrets.

Direct answer

Hosting platforms intentionally give Preview, Production, and Development different configuration scopes. Client-visible values can be frozen at build time. Adding or changing environment variables typically applies to new deployments only, not the deployment you are already staring at.

Before you rewrite, walk the Diff Worksheet below: environment parity → auth and callback URLs → data differences → build and runtime flags → network and host differences → still unexplained. Unexplained leftovers belong in a private evidence pack you keep, with non-sensitive labels recorded in the Release Evidence Check, or in a bounded structural inquiry—not in a sales-call rebuild.

Why preview and production diverge

1. Different environment scopes

On Vercel, environment variables can be scoped separately to Production, Preview, and Development (plus custom environments on some plans). Production applies to production-branch / production deployments; Preview applies to non-production branch deployments; Development is for local workflows such as vercel env pull / local run. See Vercel’s environment variables docs and the deployments / environments overview.

Practical meaning: A key present in Preview can be missing, different, or intentionally weaker in Production—or the reverse. “It worked on the preview URL” often means “it worked with Preview-scoped values.”

2. Changes apply to new deployments only

Vercel documents that changes to environment variables are not applied to previous deployments; they apply to new deployments. After adding variables, you need a redeploy for the running path to pick them up. Primary sources: Environment variables (“Any change you make to environment variables are not applied to previous deployments, they only apply to new deployments”) and How to add Vercel environment variables (redeploy after adding vars; existing deployments keep prior values).

Practical meaning: Dashboard edits without a new deployment are a common false “still broken” signal.

3. Build-time freeze for NEXT_PUBLIC_ values

Next.js documents that variables prefixed with NEXT_PUBLIC_ are inlined at build time into the client bundle. After the build, the app does not magically pick up later runtime changes to those values; they are frozen with what was present when next build ran. Source: Next.js — Environment Variables (bundling for the browser; freeze after build).

Practical meaning: Fixing a public client config often requires a rebuild, not only a runtime env tweak. Promoting an artifact built in one environment into another can carry the wrong inlined values.

4. Auth callbacks, data, and hosts

Even with matching code:

  • OAuth / magic-link callback URLs often allowlist only certain hosts (localhost is not a preview domain, and neither is production).
  • Preview databases are frequently empty or seeded; production has real rows, constraints, and worse edge cases.
  • CORS, cookie domains, and absolute URL helpers can diverge by host.
  • Feature flags and “demo mode” shortcuts may be on in Preview and off (or missing) in Production.

None of these require a mysterious framework bug. They require a parity check.

What still needs observed evidence

A green preview does not buy you:

  • Proof that production auth boundaries hold for real users
  • Proof of restore / release ownership
  • Proof that secrets are handled correctly in the live path
  • Proof that critical workflows were observed under production configuration

When you need a structured acceptance pack, use the Release Evidence Check. This guide does not replace that checklist. For why “CI green” is also not enough, see What a passing build does not prove. For whether unexplained gaps argue assess versus rewrite, see Assess, repair, or rebuild. Cost questions belong in the running-cost calculator, not in a panic rebuild.

Next checks (not a second acceptance checklist)

  • Retain sensitive logs, screenshots, and deployment URLs privately. Do not upload or attach them to the Release Evidence Check. That tool is browser-local and self-report only; it does not accept uploads.
  • On the checklist, record non-sensitive evidence labels and status only. Never paste secrets, tokens, customer data, or private links.
  • If structure or ownership is opaque, use assess-first framing in Assess, repair, or rebuild.
  • If “CI was green” is the comfort blanket, read What a passing build does not prove.
  • If you are also leaving a builder, the portability checklist covers export ownership separately from preview/production parity.
