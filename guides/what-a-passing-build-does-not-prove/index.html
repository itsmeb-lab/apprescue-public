What a Passing Build Does Not Prove

The pipeline is green. Generated tests passed. Someone says “we’re good to ship / accept.” You need to know what that signal actually showed—and what it did not.

Author: AppRescue. Reviewed 13 September 2026. Status-check claims are anchored to GitHub Docs. This page does not publish a second acceptance checklist.

Direct answer

A reported green status only proves what the configured and executed status or check actually established for that commit—not that production is correct, secure, or operable, and not that every intended check ran. On some systems a skipped job can still report success.

Status checks on GitHub “show whether commits meet the conditions set for a repository” (builds, tests, scanning hooks, deployment checks, and similar). They help reviewers decide if a pull request is ready to merge under repo-defined rules. They are not a substitute for observed production evidence. Source: GitHub Docs — About status checks.

Also material: a skipped job can report Success and may not block merge even when marked required. Same GitHub Docs page: “A job that is skipped will report its status as ‘Success’. It will not prevent a pull request from merging, even if it is a required check.”

So: a pipeline color is not production proof, and a green mark is not evidence that skipped, unconfigured, or unexecuted work ran. Use the mapping table below, then collect missing evidence with the Release Evidence Check. This page intentionally does not publish a second acceptance checklist.

Why green CI feels like safety

Status checks are visible, binary, and socially calming. In AI-built apps the comfort can be stronger: agents generate tests, the workflow stays green, and “it compiled” gets confused with “it was observed under real auth, real data, and real release ownership.”

That confusion is expensive at acceptance time. Buyers hear “passed.” Sellers mean “pipeline conditions were met.” Neither statement alone answers: Can the critical workflow be shown? Who owns the accounts? Where are the secrets? What restores when something fails?

What builds and status checks often do show

Depending on what you configured and what actually executed, a successful check may show things like:

  • The commit’s configured build or package step completed
  • Configured unit or integration jobs reported success
  • A lint or typecheck job completed
  • A deployment-check integration reported a state for that commit

Per GitHub, checks and commit statuses are mechanisms for reporting whether repository conditions were met—not a universal certificate of production readiness. See About status checks.

What they often do not prove

Without claiming a vulnerability catalog or promising a pen-test, these gaps are common:

  • Authorization / tenancy — tests that never assert “user A cannot see user B”
  • Production configuration — Preview-scoped secrets, different callbacks, frozen NEXT_PUBLIC_* values (see Why preview works but production differs)
  • Payments and webhook edge paths — happy-path mocks are not live processor behavior
  • Restore / release ownership — a green build is not a proven backup restore or known account ownership
  • Skipped work disguised as success — skipped jobs reporting Success (GitHub Docs)
  • Generated tests that mirror the bug — coverage of the wrong behavior stays green

This is an explainer, not a scanning product.
