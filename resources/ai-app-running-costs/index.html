Guide · documents, not a live bill audit

The builder plan is not the running bill.

Paying for an AI app builder buys time in the editor. The deployed app can still consume hosting, database, bandwidth, email, and model calls. Those lines can share a credit balance or sit on a usage invoice. They are still a different job than “send another prompt.”

Author: AppRescue. Reviewed 13 September 2026 from primary vendor documentation. This page does not quote a current price list or name a cheaper vendor.

Use your own numbers. Put invoice figures into the running-cost calculator. Hypothetical calculator examples are not vendor presets. Before you hand an app to a client, pair this with the Release Evidence Check.

Two meters, even when they share a wallet

Lovable’s credits-and-usage documentation describes one workspace credit balance that pays for three different usage types: build messages in the editor, Cloud usage for hosting and the built-in backend, and AI gateway usage for model calls the deployed app makes. Usage-specific grants (daily build credits, a monthly Cloud grant, a monthly AI grant) are spent first; leftover Cloud or AI use then draws general credits so a live app can keep running after a grant empties. Unused usage-specific grants do not roll over. Source: Lovable, Credits and usage.

That design is why a “quiet” month in the editor is not proof of a quiet production month. A published app can still burn Cloud and AI gateway credits while nobody opens the builder.

Replit’s publishing-and-database billing documentation meters a different split: outbound data transfer, Autoscale compute units, and request counts for published apps, plus compute time and storage for production PostgreSQL. Development databases are described as free; production databases are not. Only egress counts against the outbound-transfer allowance; ingress is described as free. Autoscale compute units combine RAM-seconds and CPU-seconds. Static deployments are described as not consuming compute units. Source: Replit, Publishing and Database Billing.

Credits, grants, and variable usage

Treat credits as a prepaid unit, not as a cap. On Lovable, Cloud usage is driven by database instance size and activity, database storage, network, file storage, compute, and realtime traffic. AI gateway usage is separate from the builder agent and scales with model, tokens, and call volume. When the workspace balance hits zero, Lovable’s documentation says building stops, deployed AI features fail, and built-in backend services can pause shortly afterward; the published site can stay up while the backend is paused. Data remains, but the same page says you cannot access or export Cloud data until services run again. Source: Lovable, Credits and usage.

On Replit, publishing overages and production-database hours accumulate against monthly credits, then bill when usage exceeds those credits or at the monthly cycle. A production database stays “active” while it receives requests and for an additional five minutes; idle databases suspend. Empty PostgreSQL still occupies a documented default storage footprint. Source: Replit, Publishing and Database Billing.

When you model this in the calculator, included allowance is subtracted from usage units once. Do not also subtract it as a dollar credit.

Budgets and billing settings are not a guaranteed spend cap

Lovable documents auto top-up with a threshold, a top-up amount, and an optional monthly spend limit for automatic purchases. Long-running build check-ins are described as a notification threshold, not a hard cap; a run can pass the level before it pauses. Member credit limits apply to build usage only; Cloud and AI gateway (run) usage do not count against a member’s monthly build limit. Source: Lovable, Credits and usage.

Replit documents usage limits and a service shutdown limit under Settings → Account → Usage → Manage limits, plus credit packs that expire six months after purchase and do not roll over. Usage limits and budgets apply after credit packs are consumed. Auto-reload can buy another pack when the balance is low. Those controls can block further usage-based services after a limit; they are not a promise that every charge path is covered, or that a published app will degrade gracefully. Source: Replit, Managing Your Spend.

We do not guarantee that any slider you set will cap spend. Verify the current wording in your own billing UI; vendor copy changes.

Domain, email, and database are separate lines

A custom domain is usually paid to a registrar and pointed with DNS you control. That invoice is not the builder subscription. Transactional email is typically a connector or a third-party provider; Replit’s project-help documentation describes connecting a service such as Resend through Tools → Connectors and adding DNS records at your DNS provider. Source: Replit, Projects and files.

Database cost follows production data and instance size, not the fact that a table exists in development. Lovable Cloud instance size and storage are managed under More → Cloud → Overview → Advanced settings; a larger instance uses more credits as the app runs, and paused Cloud still incurs storage because data stays in place. Source: Lovable, Advanced settings.

Verification steps (your account, your figures)

  1. Open the vendor billing screen named in the docs above (Lovable: Settings → Plans & credit usage and Usage details; Replit: Settings → Account → Account usage). Record the observation date.
  2. Split last month into builder/editor usage versus published-app usage (Cloud / run credits, outbound transfer, compute units, production database hours).
  3. Write down included grants or allowances and any overage. Do not assume unused grants roll over unless the current docs say they do.
  4. Confirm whether auto top-up, auto-reload, or a usage limit is on, and what happens at zero balance (pause, blocked usage, or continued storage charges).
  5. Enter those numbers in the calculator. Leave unknown fields blank.
  6. If you are preparing a handoff, record what you actually tested in the Release Evidence Check.
